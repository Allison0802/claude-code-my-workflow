# `method-evolve` Skill — Design Specification

**Status:** DRAFT — pending user review
**Author:** drafted with Claude (brainstorming skill)
**Date:** 2026-04-21
**Related paper:** Tsinghua FIB Lab, *AutoSOTA: An End-to-End Automated Research System for SOTA Model Discovery* (2026)

---

## 1. Goal

A cross-project Claude Code skill that applies an **evolutionary code-search loop** (FunSearch / AlphaEvolve / AutoSOTA stage-3 pattern) to statistical methods in this repository. The skill introspects the current sub-project, interviews the user to fill gaps, generates a project-specific configuration, and drives a generation-chunked search that proposes, evaluates, and ranks variants against hard statistical gates.

**Why this instead of a one-off script.** The same loop structure is useful for:
- IPW propensity feature sets (Missing Types, v1 reference example)
- RPM / DR augmentation forms (Missing Types, v2)
- Cox / RF hyperparameter or feature sets (comparisons, v2)
- Future sub-projects with a configurable slot and a Monte Carlo evaluator

Hardcoding any one of these produces a single-use script. A config-driven skill amortizes the engineering effort across the dissertation.

---

## 2. Non-goals (explicitly out of scope for v1)

- **Auto-discovery of method improvements from raw PDFs** (AutoSOTA phases 1–2). v1 assumes the user has a working simulation harness.
- **Additional slot kinds beyond `feature_set`.** Engine supports a pluggable `slot.kind`; v1 ships only `feature_set` and errors cleanly on unknown kinds.
- **Cross-estimator joint evolution.** v1 evolves one slot for one estimator.
- **Multi-island or MAP-Elites samplers.** Single-population elitist sampling for v1.
- **Direct Anthropic API proposer.** Subagent via Task tool only.
- **GPT / Codex reviewer loop on variants.** The Monte Carlo score is the critic.

## 3. Architecture

**Two-layer split:**

```
┌──────────────────────────────────────────────────────────────┐
│  method-evolve skill (domain-agnostic, parent repo)          │
│    .claude/skills/method-evolve/                             │
│      SKILL.md                                                │
│      workflow phases, DB format, sampler, validator,         │
│      subagent proposer template, report generator            │
└──────────────────────────────────────────────────────────────┘
                           │ reads
                           ▼
┌──────────────────────────────────────────────────────────────┐
│  config.yaml (project-specific, generated by Phase 0–1)      │
│    <subproject>/quality_reports/evolve/                      │
│      YYYY-MM-DD_<name>/config.yaml                           │
│    slot whitelist, fitness, gates, evaluator env vars,       │
│    baselines, budget — everything domain-specific            │
└──────────────────────────────────────────────────────────────┘
                           │ drives
                           ▼
┌──────────────────────────────────────────────────────────────┐
│  Generated driver (per-run, project-specific)                │
│    <subproject>/scripts/R/evolve_<name>_driver.R             │
│    <subproject>/scripts/slurm/evolve_<name>.sh               │
│    Uses existing method-comparison script as evaluator.      │
└──────────────────────────────────────────────────────────────┘
```

**Key invariant.** The skill contains no IPW-, RPM-, or Cox-specific logic. All domain knowledge flows through `config.yaml`.

## 4. Workflow — four phases

Entry points mirror the `method-derive` pattern (checkpointed, resumable):

```
/method-evolve scan  <subproject>       # Phase 0: introspect, draft config
/method-evolve setup <name>             # Phase 1 + 2: interview, scaffold, smoke test
/method-evolve run   [max_gens: N]      # Phase 3: advance N generations, checkpoint
/method-evolve promote                  # Phase 4a: submit top-K at full tier
/method-evolve report                   # Phase 4b: leaderboard + final report
```

### Phase 0 — Introspect (`scan`)

Skill walks the current sub-project and emits a draft config with `# VERIFY` comments on every inferred field.

**Detection heuristics:**
| Field | Primary signal | Fallback |
|---|---|---|
| Evolvable slot | `# @EVOLVE` annotation comments | regex: `feature_set = `, `formula = ~`, `model.matrix(`, hyperparam list literals |
| Evaluator script | `*_comparison_*.R`, `*_method_*.R` naming | user-provided path |
| Metrics | numeric columns in latest results RDS | match to catalogue `{c_index, brier, ibs, bias, coverage, calibration}` |
| Baselines | scripts matching `*oracle*`, `*cca*`, `*full*`, `*null*` | user-provided paths |
| Scenarios | env-var patterns in `submit_*.sh` | user-picked scenario name |
| Covariate whitelist | DGP function signature + `compute_*_features` helpers | user-edited list |

Output: `config.draft.yaml` in the run's dated subfolder.

### Phase 1 — Configure (`setup`, interactive)

For each `# VERIFY` field, prompt the user (multiple-choice where possible, free-text where not). User edits gate thresholds, budget, slot selection. Final `config.yaml` is written and committed.

### Phase 2 — Scaffold (`setup`, still)

From `config.yaml`, generate:
1. **Evaluator shim** — one-line patch to the chosen method-comparison script: load `$FEATURE_SET_FILE` (or the config-declared slot env var), inject into the slot, continue as today.
2. **Driver R script** — `scripts/R/evolve_<name>_driver.R`.
3. **SLURM submit** — `scripts/slurm/evolve_<name>.sh` if the sub-project uses SLURM.
4. **Smoke test** — run one generation with `batch_size = 2`, validate the full loop (subagent proposer → validator → evaluator → DB write → checkpoint). If smoke fails, surface the error, stop, wait for user fix, resume.

### Phase 3 — Run (`run`, resumable)

Read `EVOLVE_STATE.json`. Advance up to `max_gens` generations (default 5). Per generation:

1. **Propose** — Task subagent (Claude Opus, `model: "opus"` explicit) sees top-3 gate-passers by primary fitness + 1 random gate-passer as parents. Prompt includes grammar spec, whitelist, and a list of previously-failed patterns from the DB. Returns JSON array of `batch_size` candidate feature sets.
2. **Validate** — AST/regex grammar check. Invalid variants recorded in DB with `grammar_valid = false` and `failure_reason`; they never cost MC time.
3. **Evaluate (Screen tier)** — valid variants submitted in parallel (`n_workers`) to the existing method-comparison script with `FEATURE_SET_FILE` set. Each runs `B = 50` seeds at `N = 500` in the hardest single scenario. Single-threaded per variant (no nested `mclapply`).
4. **Score** — compute `recovery_IBS` and all gate metrics from the variant's output RDS.
5. **Write DB** — append one JSONL line per variant.
6. **Checkpoint** — update `EVOLVE_STATE.json` atomically.
7. **Early-stop check** — if `early_stop_after` generations have passed with no improvement in the top-5 primary fitness, halt.

Exit cleanly at end of `max_gens` (or on early-stop). User re-invokes `run` to continue.

### Phase 4 — Promote & Report

- **`promote`** — submit top-`promote_top_k` gate-passing variants to the full-tier evaluator (full B, full scenario grid) using the existing `submit_*.sh` pattern. Records results under `full.*` fields in the DB.
- **`report`** — generate `leaderboard.md` (ranked top-20), `final_report.md` (winner, recovery analysis, feature-frequency across top variants, comparison to the project's hand-crafted baselines), and plots (fitness-by-generation, top-feature frequencies).

## 5. Slot grammar — pluggable kinds

The grammar engine dispatches on `slot.kind`. v1 ships one kind; the interface is frozen so v2 can add more without breaking existing configs.

### v1: `feature_set`

```
feature_set   := list of terms, length ≤ slot.max_terms
term          := base | transform(base) | base1 * base2
base          ∈ slot.whitelist
transform     ∈ slot.transforms
interactions  ∈ {none, pairwise, three-way}   # v1: pairwise only
```

**Validator** — pre-evaluation, no code execution required:
1. Parse each proposed term with a minimal R-formula AST walker.
2. Every `base` must be in `slot.whitelist`.
3. Every `transform(base)` must use a transform from `slot.transforms`.
4. Interactions must respect `slot.interactions`.
5. No term may match any pattern in `slot.forbidden_patterns` (regex).
6. `length(feature_set) ≤ slot.max_terms`.

Rejections return the specific failure reason; the subagent sees these in its prompt so the loop learns the boundary.

### v2+ slot kinds (declared here, not implemented)

- `formula` — full R formula with whitelist
- `hyperparameters` — bounded numeric/categorical hyperparam set
- `augmentation_fn` — a function body in a typed grammar (e.g., DR augmentation)
- `model_config` — structured config dict

## 6. Config schema

Full YAML schema. All fields required unless marked `# optional`.

> **Note on example values.** Every concrete value below is illustrative and
> tied to the Missing Types / IPW reference case. The **schema keys are
> fixed** (the engine looks for these specific field names); **values are
> user-/project-supplied** — populated by `scan`, refined in `setup`, then
> frozen in `config.yaml`.

```yaml
name: ipw-feature-search                 # short run name, used in paths

target_script: missing_types_method_comparison_ipw.R
# ^ path relative to subproject root

evaluator:
  env_vars:                              # env vars passed to target_script
    SCENARIO_NAME: high_mar_high_cens
    N_SIMS: 50
    N_SUBJECTS: 500
    FEATURE_SET_FILE: ${VARIANT_PATH}    # skill substitutes per variant
  results_file_pattern: "results_missing_types/${SCENARIO_NAME}_${VARIANT_ID}.rds"
  # ^ where the eval's output lands, used to extract metrics.
  # Substitutions resolved per variant:
  #   ${VARIANT_PATH} — absolute path to variants/var_NNNNN.rds
  #   ${VARIANT_ID}   — the string "var_NNNNN" (zero-padded sequence)

slot:
  kind: feature_set
  max_terms: 20
  whitelist:
    - age
    - sex
    - n_prior_type1
    - n_prior_type2
    - prev_event_type
    - time_since_last_type1
    - time_since_last_type2
    - log_time
    - e.time
  transforms: [log, sqrt, "I(^2)", "ns(df=3)", "ns(df=4)"]
  interactions: pairwise
  forbidden_patterns:
    - "^true_"
    - "^type$"
    - ".*_future$"

fitness:
  primary: recovery_IBS
  primary_definition: "(IBS_CCA - IBS_IPW) / (IBS_CCA - IBS_oracle)"
  # ^ computed in R from the metric columns present in results RDS

  gates:
    - {metric: abs_bias, op: "<",  threshold: 0.02}
    - {metric: coverage, op: in,   range: [0.93, 0.97]}
    - {metric: c_index,  op: ">=", expr: "C_CCA - 0.01"}

baselines:
  # Baselines MUST be evaluated on the same scenario and DGP as the screen
  # tier. Mismatched N or scenario invalidates the recovery ratio denominator.
  # If only full-tier baselines exist, `setup` warns and offers to run a
  # scenario-matched baseline pass once at setup time (cheap: 2 runs).
  scenario_match_required: true
  oracle: {results_file: results_missing_types/oracle_hard.rds}
  CCA:    {results_file: results_missing_types/cca_hard.rds}
  # ^ used to compute the denominator of recovery_* metrics

budget:
  max_variants: 200
  batch_size: 10
  max_generations: 20
  promote_top_k: 10
  early_stop_after: 5    # generations with no top-5 improvement
  # n_workers lives in compute.screen.n_workers (authoritative)

compute:
  # Where each tier runs. v1 supports local Screen + Longleaf Full only.
  screen:
    backend: local                # Mac, parallel across variants
    n_workers: 5                  # parallel variant evals; keep < physical cores
    variants_cache: ~/.method-evolve-cache/${run_date}_${name}
    # ^ non-synced local dir for the many small variant RDS files;
    # keeps OneDrive out of the hot path
  full:
    backend: longleaf
    existing_submit: submit_missing_types_ipw.sh
    # ^ the project's existing full-tier submit; skill generates a
    # promote-variant wrapper that pins FEATURE_SET_FILE per top-K variant
    remote_host: ""               # optional; used only to PRINT rsync/ssh
    remote_path: ""               # commands in `promote` output. Skill does
    # ^ not SSH on your behalf in v1 — you run them yourself.

paths:
  # ${run_date} resolves to ISO date YYYY-MM-DD at `setup` time, frozen
  # in config.yaml thereafter so re-invocations of `run` target the same
  # folder. ${name} is the top-level `name:` field above.
  out_dir: "quality_reports/evolve/${run_date}_${name}"
  variants_dir: "${out_dir}/variants"
  program_db:   "${out_dir}/PROGRAM_DB.jsonl"
  state_file:   "${out_dir}/EVOLVE_STATE.json"
```

## 7. Fitness evaluation

### 7.1 Primary metric — integrated Brier score (IBS)

Not present in the current Missing Types harness. **Adding this is a prerequisite** for `method-evolve setup` against IPW. Specifically:

- Evaluate Brier on a **small time grid** (default: 5 points evenly spaced across the evaluable horizon — exact grid pinned in config under `fitness.time_grid`).
- For pseudo-observation models, use **pseudo-Brier**: $\tfrac{1}{n} \sum_i (Y_i(t) - \hat{\pi}_i(t))^2$ with pseudo-obs $Y_i(t)$ in place of IPCW weights.
- Integrate uniformly over the grid (trapezoidal rule).
- Record `IBS` as a column in the evaluator's output RDS, alongside existing `c_index`, `bias`, `coverage`.

**Open sub-decision (flag for review):** IPCW-weighted Brier (Gerds–Schumacher) vs. pseudo-Brier. Pseudo-Brier is cleaner given the project already computes pseudo-observations. Default to pseudo-Brier unless the user objects.

### 7.2 Gates (all must pass, else discard from leaderboard)

- `|bias| < 0.02` — relative bias of the primary effect estimate (existing project convention)
- `coverage ∈ [0.93, 0.97]` — nominal 95% CI coverage
- `c_index ≥ C_CCA − 0.01` — floor prevents degenerate winners that trade discrimination for calibration

Failed variants are kept in the DB with `gate_pass: false` and per-gate failure flags — used as negative examples in future subagent prompts.

### 7.3 Recovery ratio

```
recovery_IBS = (IBS_CCA − IBS_IPW) / (IBS_CCA − IBS_oracle)
```

Bounded ~[0, 1] in the typical case. Values > 1 mean the variant *beat* the oracle — keep but flag for manual inspection (usually MC noise or a lucky seed; promotion to Full tier resolves).

## 8. Program DB and sampler

### 8.1 DB format

Append-only JSONL, one variant per line:

```json
{
  "variant_id": "var_00042",
  "generation": 4,
  "parent_ids": ["var_00031", "var_00028", "var_00035", "var_00019"],
  "feature_set_expr": ["age", "log(log_time)", "age*sex", "ns(e.time, df=3)"],
  "grammar_valid": true,
  "screen": {
    "ibs_ipw": 0.142,
    "ibs_recovery": 0.68,
    "c_index": 0.721,
    "abs_bias": 0.011,
    "coverage": 0.948,
    "gate_pass": true
  },
  "full": null,
  "llm_response_id": "gen_04_variant_02",
  "timestamp": "2026-04-21T23:17:04-04:00"
}
```

### 8.2 Sampler (parent selection)

v1: top-3 gate-passers by primary fitness + 1 random gate-passer (diversity injection).

Rationale: pure elitism converges too fast on small search spaces; the random draw keeps the proposer exposed to non-top regions. Documented here so v2 can justifiably swap in islands / MAP-Elites.

## 9. Subagent proposer prompt

Fixed template filled from `config.yaml` at runtime. Structure:

```
[System — persona: "expert statistical methodologist"]
[Project context: brief description of the slot + estimator + DGP]
[Grammar specification: whitelist, transforms, interactions, forbidden patterns, max_terms]
[Parent variants (top-3 + 1 random): for each, show feature_set_expr + screen scores]
[Failed-variant negative examples: up to 5 grammar-invalid variants with failure reasons]
[Task: propose BATCH_SIZE new feature sets as a JSON array; each must satisfy the grammar.]
[Output format: strict JSON schema]
```

`model: "opus"` is **always explicit** (per `.claude/rules/codex-fallback-protocol.md` — never inherit parent's Sonnet).

No reviewer loop; the subagent's output goes straight to the grammar validator.

## 10. Runtime model

### 10.1 Where each tier runs

**v1 is a two-environment split — local Mac for Screen, Longleaf for Full.**

| Tier | Environment | Mechanism | Why |
|------|-------------|-----------|-----|
| Skill workflow (subagent, DB, validator, reports) | **Local Mac** (Claude Code session) | native | Where your Claude Code session already lives |
| Screen MC evals (B=50, N=500, hardest scenario, ~2–3 min each) | **Local Mac** | parallel R subprocesses via `mclapply` across variants, single-threaded within each | Fast feedback, no queue wait, no SSH, no OneDrive contention; matches your "test locally first" convention |
| Full MC evals (top-K at full B + full scenario grid) | **Longleaf** via existing `submit_missing_types_ipw.sh` | skill generates a promote-wrapper submit script; user `rsync`s + `sbatch`s manually | Same workflow you already use for every other method — no new login/automation |
| Program DB, logs, reports | **Local** (OneDrive-synced) | native filesystem | Visible across machines; tracked alongside `quality_reports/` |
| Variant RDS cache (many small files) | **Local, non-synced** (`~/.method-evolve-cache/…`) | native filesystem | Avoids hammering OneDrive sync with per-variant writes |

**The skill does not SSH, authenticate, or submit on your behalf in v1.** `promote` ends by printing the exact `rsync` + `ssh` + `sbatch` commands for you to run. SSH-automated promotion is a v2 feature gated behind an explicit `compute.full.ssh_submit: true` opt-in.

### 10.2 Process mechanics

- **Parallelism:** `compute.screen.n_workers` variants evaluated concurrently per generation (default 5). Each variant is single-threaded internally (50 seeds sequential). No nested `mclapply`. Leaves headroom on your Mac for other work.
- **Session boundaries:** one `/method-evolve run` call advances up to `max_gens` generations, then cleanly checkpoints and exits. User re-invokes to continue.
- **Checkpoint durability:** `EVOLVE_STATE.json` written atomically after every generation (write to `.tmp`, then rename). Partial generations are rolled back on restart.
- **Failure modes:**
  - Subagent timeout → retry once with a shortened parent context; if still fails, stop generation and checkpoint.
  - Grammar validator rejection → record and continue (normal).
  - Evaluator crash (local R process) → record variant with `screen.status: "eval_error"`, continue generation.
  - Local R missing a package → surfaced during Phase 2 smoke test, not mid-run.
  - Longleaf Full-tier timeout → user's problem, not the skill's (skill already exited after printing `sbatch` commands).

1. **Add IBS to the MC output.** Patch `missing_types_method_comparison_ipw.R` (and companions if cross-method recovery is desired) to compute pseudo-Brier at each time in `fitness.time_grid` and record the integrated value under column `ibs`. ~20 LoC addition.
